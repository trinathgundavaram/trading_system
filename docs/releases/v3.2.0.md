## Why this release exists

Two inputs converged: an external technical audit
(`trading_system_detailed_audit_v3_1_0` + its executive summary) was reviewed
against the current tree, and separately the Learning tab's "Automated
Learning Loop" panel was reported failing with "Couldn't load this panel"
after loading briefly. Both are addressed here. Every audit finding was
checked against the live code first — several (e.g. the double
qualification-multiplier application) were already fixed in v3.1.0 and are
not repeated; only findings still reproducible in this tree were changed.

## What changed

### Learning loop / pattern database

- **P1-01 — bucket7_score dropped from the learning schema.**
  `rules/swing_buy_rules.py` scores 7 buckets (VOLATILITY_EXPANSION added),
  but `learning/pattern_database.py`'s `NUMERIC_FEATURES` only listed 6, so
  `bucket7_score` was computed and stored in every pattern row but silently
  excluded from similarity encoding — the live scorer and the
  learning/similarity engine were operating on different feature spaces.
  `NUMERIC_FEATURES` now includes it — `learning/pattern_database.py`. Rows
  that predate this fix (the key was never written) are encoded as MISSING
  and mean-imputed, not as a measured zero — `KEY_ABSENT_AS_MISSING_NUMERIC`,
  `learning/pattern_database.py:_encode_patterns`. No schema migration:
  `features` is one JSON blob per row. The legacy `buy_result.py` fallback
  path in `engine/pattern_features.py:build_pattern_features` was one bucket
  short of the same fix and is now consistent.

### Live execution safety

- **P1-07 — portfolio-risk check failed open.** `scheduler.py`'s
  `try/except` around `PortfolioRiskEngine.evaluate()` logged and swallowed
  any exception, leaving `portfolio_risk_result = None` — the block-gate
  further down only fired on `portfolio_risk_result is not None`, so a
  crashed risk engine silently removed the only thing standing between a
  signal and an unbounded-concentration **live** trade. Live mode now fails
  CLOSED on an unevaluable portfolio-risk check (blocks the buy, logs it,
  records the rejection as `portfolio_risk_unavailable`). Paper mode is
  unchanged — advisory only, since nothing real is at stake and blocking it
  would also break paper trading on a transient bug.
- **P1-08 — live equity excluded cash.** `rules/risk_rules.py:daily_loss_limit`
  computed paper-book equity as cash + deployed capital, but live-book equity
  as deployed capital only, understating live equity and making the
  percentage-based daily-loss limit tighter than intended.
  `engine/live_trader.py:account_cash` (new) reuses the same Robinhood
  profile call `_buying_power()` already makes before every live order,
  reading `cash` specifically (not `buying_power`, which can include margin
  and would overstate equity in the other direction). Falls back to the
  pre-fix figure if the account isn't reachable — a reachable account gets a
  more accurate (wider) limit; an unreachable one is no worse off than before.

### Learning tab / UI

- **Root cause of the reported panel failure.** Two real
  `backtest_runs` subprocess logs from production were completely empty —
  zero bytes, not even the first `print()` in `run_backtest.py`'s `main()`,
  which runs before any network call. The only thing between process start
  and that line is `load_config_dict()` → `secrets.get()` → the OS keyring
  probe, and a Keychain "Allow access?" prompt from a freshly-spawned,
  non-interactive subprocess has no window-server session to answer it — the
  call blocks forever, and neither `run_and_persist()`'s failure handling nor
  anything else downstream ever runs, so nothing is ever recorded as failed.
  `storage/secrets.py`'s keyring reads (`_backend()`'s probe and
  `_keychain()`'s per-secret reads) are now timeout-guarded
  (`TP_KEYRING_TIMEOUT_S`, default 5s, via `_run_with_timeout`'s daemon-thread
  wrapper) — a stuck OS permission prompt can no longer hang the process
  indefinitely; it falls back to the environment/`.env`, same as a genuinely
  absent keyring.
- **Defensive fix, same bug class as the already-fixed Performance/Strategy
  tabs.** `renderLearningTab`'s "Automated Learning Loop" panel
  (`ui/index.html`) wrapped only the `fetch` in `try/catch`, not the
  HTML-building after it — any exception while rendering the rule-attribution
  table or the champion/challenger summary was an *uncaught* rejection (panel
  stuck on "Loading…", console-only error), not the "Couldn't load this
  panel" message the code appears to promise. The whole body is now one
  `try/catch`.
- `ChampionChallenger.evaluate()`'s "challenge not found" path
  (`learning/champion_challenger.py`) returned neither `ready` nor `message`,
  which the panel rendered as the literal string "undefined". Now returns
  `ready: false` with a `message`, consistent with every other non-ready
  return from that method.

## What this does NOT change

No scoring, sizing, or exit logic moved — `scripts/classify_change.py`
reports MINOR. `rules/swing_buy_rules.py`, `rules/sell_rules.py`,
`rules/exit_scorer.py`, `rules/dynamic_thresholds.py`, `rules/hard_vetoes.py`
and `config.yaml` are untouched, so pre- and post-release trade history
remains poolable. No database schema changed. No config keys changed.

## Behaviour you will notice

- A live-mode BUY signal now gets **blocked** (not silently allowed) if the
  portfolio-risk engine throws — previously invisible, now logged as
  `BUY blocked - portfolio risk could not be evaluated` and recorded in
  `rejected_signals` under stage `portfolio_risk_unavailable`.
- Live-book `daily_loss_limit` may compute a slightly larger (more accurate)
  dollar figure than before, if the Robinhood account is reachable when it's
  evaluated.
- The Learning tab's rule-attribution table now includes bucket 7
  (Volatility Expansion) in similarity matching for new patterns going
  forward; nothing changes for already-closed patterns beyond how they're
  encoded at query time.
- Any process that resolves secrets (server.py, scheduler.py,
  `run_backtest.py`, etc.) now gives up on a hung OS keyring prompt after
  `TP_KEYRING_TIMEOUT_S` seconds (default 5) instead of hanging forever, and
  logs a warning naming the secret when it does. A one-time interactive
  Keychain "Allow access?" prompt in a genuinely interactive session still
  has 5 seconds to be answered before falling back — increase
  `TP_KEYRING_TIMEOUT_S` if that's ever too tight for a real prompt you
  intend to click.

  `decision_function_changed: false` and no scoring/rule code changed.

## Rollback

```bash
./scripts/tp promote v3.1.1
```

Rolling back reinstates: the bucket7/learning feature-space mismatch, the
fail-open portfolio-risk gate in live mode, the live/paper equity asymmetry
in `daily_loss_limit`, and the unguarded keyring calls (so a backtest
subprocess can hang silently again). No schema moved, so v3.1.1 can read a
database this version has written without any migration concerns.

## Known issues carried forward

Everything listed under v3.1.0/v3.1.1 still applies, plus the broader P0/P1
items from the external audit not addressed in this release because they are
validation/process work rather than code defects: walk-forward and
independent-holdout validation have not been (re-)run, `pandas_ta` vs
`ta_fallback` backend equivalence is not yet quantified, order lifecycle
still lacks a durable `UNKNOWN_ORDER_STATE` + reconciliation state machine,
`account_id` is not yet a mandatory field on positions/trades/orders, and
`config.yaml` still has no schema validation at startup.
