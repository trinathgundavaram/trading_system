## Why this release exists

Phase 2.5 (§48–§55). It sits between Phase 2 and Phase 3 for one reason: Phase
4 recalibrates the scoring function against measured history, and the history
it would have recalibrated against was not honest.

The excursion table had duplicate rows and unresolvable joins; the exit
vocabulary was free text, so "which rule closed this" could not be answered
mechanically; the drawdown caps in `config.yaml` disagreed with the tooling
that printed them; and two risk flags nothing ever wrote were being read by
three modules as though they were live controls — one of them as a
priority-1 exit-everything trigger.

Recalibrating against that is not measurement. This release fixes the base.

## Why this is v2.0.0

`docs/PHASE2_5_PLAN.md` suggested v1.4.0 for the decision-neutral half and
v1.5.0 for §48/§52/§53. The work shipped as one body, and §53 is in it.

§35's rule is not a versioning preference. §53 changes which quantity
`engine/portfolio_risk.py` counts as an open high-volatility position, and
portfolio risk both sizes positions and can block entries. The count becomes
*stricter* — the old proxy read low — so expect marginally more size reduction
around volatile names. That means trades recorded before this tag and after it
came from different strategies, and pooling them is a measurement error. A
minor bump would have hidden that boundary exactly where someone six months
from now will fail to look for it.

Pattern rows remain poolable individually. Anything reasoning about position
sizing across this boundary must account for it.

## What changed

The full section-by-section account is in `CHANGELOG.md` under `[2.0]`, and the
plan and the adjudication of the 2026-07-25 external review are in
[docs/PHASE2_5_PLAN.md](docs/PHASE2_5_PLAN.md) and
[docs/PHASE2_5_REVIEW_ADJUDICATION_2026-07-25b.md](docs/PHASE2_5_REVIEW_ADJUDICATION_2026-07-25b.md).
In summary:

- **§48** the paper-ledger reset, so the equity curve has one epoch rather than
  a re-seed discontinuity running through it
- **§49–§51** the excursion table: purge the duplicates, add the integrity
  constraints, and make the join safe
- **§52** drawdown cap tooling — the values themselves wait on a clean curve
- **§53** the high-volatility position count (**the decision change**)
- **§54** removal of `daily_loss_limit_triggered` / `daily_profit_lock_triggered`,
  two config keys nothing ever wrote and three modules read as live controls
- **§55** `rejected_signals`, so a blocked entry is recorded instead of vanishing
- **§C1–§C3, §D** the second review's follow-ups: structured exit codes at the
  decision point, the `mae_mfe` foreign key, a gated seed-paper command

`classify_change.py` reports MAJOR, and most of that is its conservative
heuristics — `engine/rules_catalog.py` changed only in description strings,
and the `migrations/` rule fires on additive columns and indexes.
`config_fingerprint` is **unchanged at `cc9a149613427f56`**. §53 is the one
change that genuinely moved a decision, which is why it is called out
separately rather than left inside that paragraph.

## What this release does NOT claim

Several pieces are code-complete but not yet **run**, because they are
destructive and need the live database. This is not a caveat, it is the
operating instruction:

- **§48's reset has not been run.** Take `scripts/tp backup` first, and read
  `scripts/assess_test_damage.py`.
- **Migrations 009–012 are not applied.** 010 fails while duplicate
  `trade_id`s remain and 012 raises on any orphan — those failures are the gate
  on §49's purge, not bugs. `scripts/phase2_5_cutover.sh` sequences the whole
  thing.
- **§52's cap values are unchanged.** The tooling is in; the numbers need a
  clean curve, so they wait on §48.
- **§53's `high_vol_atr_pct_threshold` is unchanged at 5.0.** Recalibrating it
  is now worth doing — before this change it would have been tuning against the
  wrong axis.
- **§55's threshold is unchanged at 3.** It needs a week of real rows.

## Re-validation

`revalidation_required: true`. §53 moved a decision, so the §32 live-arm gate
must be re-satisfied before live execution is armed — including the 30
consecutive paper days with positive net expectancy, measured on rows produced
*after* this tag. Pre-2.0 paper history does not count toward it.

## Rollback

Safe as long as the migrations have not been applied. `git checkout v1.3.1`
restores the previous code; 009–012 are additive (nullable columns, indexes, a
foreign key), so a v1.3.1 process can still read a migrated database. Once
§48's reset has been run, the paper ledger it cleared is only recoverable from
the backup you took first — which is the reason that instruction is in this
note twice.
