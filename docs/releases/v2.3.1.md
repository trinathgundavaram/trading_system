## Why this release exists

v2.3.0 was correct and never ran.

`./service.sh restart` started a new UI process that could not bind port 8080,
because the old one still held it. launchd relaunched it 342 times. The browser
went on being served by the pre-v2.3.0 process, so the Robinhood fix that
release exists for appeared not to work — the code under test was never the
code answering. Nothing reported a failure: every service verb printed success,
and the only evidence was `[Errno 48] address already in use` buried in
`launchd_ui.log`.

`run.sh --ui` has handled this since the 2026-07-14 incident, and its comment
describes the symptom exactly: *"looked exactly like a frontend bug ... when it
was really 'you have two of these running.'"* §45 moved service management into
`scripts/services.py` and did not carry that cleanup across. The fix existed in
the path that was not used.

## What changed

### The restart actually replaces the running process

- **`scripts/services.py` reclaims port 8080 before starting the UI** —
  `_free_ui_port()`, called on `install`/`start`/`restart` (not `stop`, which
  has no bind to protect). Ordered stop → reclaim → start.

  Stricter than `run.sh`'s version in one respect: `run.sh` kills whatever holds
  the port on the reasoning that on a single-user dev machine it is always our
  own leftover. Usually true, occasionally expensive. This checks the command
  line and **refuses** to kill a process that is not ours, printing what is
  holding the port instead. A failed bind with a comprehensible message costs
  much less than killing an unrelated service.

  SIGTERM is escalated to SIGKILL after a poll window — a UI that ignores
  SIGTERM is still holding the socket, which is the entire failure.

- **Eight regression tests** — `tests/test_phase3_portability.py:
  TestStaleUiPortIsReclaimed`. Including one asserting `main()` actually calls
  the cleanup in the right order, because the unit can be perfect and the bug
  still ship if nothing invokes it, which is precisely what §45 did.

### The Performance tab could not recover from a 500

- **`profit_factor()` returns `None`, not `float("inf")`** —
  `analytics/performance.py`. Starlette's `JSONResponse` renders with
  `json.dumps(..., allow_nan=False)`, so an infinity in a payload raised
  `ValueError: Out of range float values are not JSON compliant` at render
  time — after the handler had returned successfully — and the route answered
  HTTP 500. `/api/analytics/performance` did this for any book with no losing
  trade. `None` matches what `engine/backtest_engine.py:569` already returns
  for the same case, and is the more truthful answer: "no losses to divide by"
  is absent evidence, not an infinite result.

  Note the grouping — `gross_loss` sums `o <= 0`, so a single break-even trade
  among winners triggers it too. A freshly installed version whose first closed
  trade wins hits it immediately, which is exactly when someone is watching
  that tab.

- **`SafeJSONResponse`** — `server.py`, now the app's
  `default_response_class`. Non-finite floats become `null` instead of taking
  the endpoint down. For the sources nobody has hit yet:
  `engine/ta_fallback.py` alone divides by `.replace(0, np.nan)` in seven
  places. Sanitising is **logged**, not silent — a NaN reaching the response
  layer is still a bug, and this must not become the reason nobody finds it.

- **`renderPerformanceTab` was the only async renderer with no error
  handling** — `ui/index.html`. It also used raw
  `fetch().then(r=>r.json())` rather than `fetchJSON`, so no HTTP status check
  and no timeout. Any failure left the panel on "Loading…" forever — the same
  symptom as the Journal tab's 2026-07-23 hang. Now `try`/`catch` +
  `fetchJSON` + `tabErrorHTML`, matching the other twelve, and the two
  `.toFixed` calls go through a new `fmtRatio()` that renders `null` as "n/a".

### The paper basis being unapplied is now visible

- **`snapshot()` reports `basis_drift`** — `engine/paper_trader.py`, surfaced
  as a banner at the top of the Portfolio tab. `ensure_seeded()` reads
  `paper_trading.starting_cash` only when CREATING a purse, so editing it on a
  live account changes nothing — correct, since silently re-basing a book
  mid-flight would corrupt every return figure computed against it, but
  previously invisible. The config said $10,000, the purse said $1,000, and the
  only symptom was "the paper cash was not updated" with nothing explaining
  why. Reported with the exact command, never acted on automatically.

## Behaviour you will notice

- `./service.sh restart` now says
  `port 8080 still held by a previous UI process (PID nnnn) - terminating it`
  when it reclaims one, and the new code actually serves afterwards.
- The Portfolio tab shows a yellow "Paper basis not applied" banner until
  `topup_paper_account.py --apply` has been run.
- Performance tab shows "n/a" for profit factor before the first losing trade,
  rather than hanging.
- A new WARNING if a non-finite float ever reaches a response payload.

## Rollback

No schema change; the previous version reads this database unchanged.

```bash
./scripts/tp promote v2.3.0
```

Note that rolling back reinstates the restart bug this release fixes, so a
subsequent `./service.sh restart` may again leave a stale process on 8080. Free
it manually:

```bash
kill $(lsof -ti tcp:8080 -sTCP:LISTEN)
```

## Known issues carried forward

- **`UI_AUTH_TOKEN` is not set on this machine**, so `_auth_token()` raises and
  every write endpoint answers 500 — kill switch, config saves, arming live
  execution, manual sell. `server.log`:
  `UI auth token is not configured: Secret 'UI_AUTH_TOKEN' not found`. §4 made
  this fail closed rather than default to empty, which is right; the value was
  simply never provisioned. Not fixable from a release — run
  `./scripts/tp secrets set UI_AUTH_TOKEN`.
- **`config_fingerprint` does not cover `risk.max_position_size_usd`** —
  carried from v2.3.0, unchanged. See that release's note.
- **The `${VAR}`-into-engine-code class is closed at one site, not
  systematically** — carried from v2.3.0.
- **`renderPositionsTab`, `renderControlTab`, `renderStrategyTab`,
  `renderLogsTab` and `renderNewsTab` have `try`/`catch` but no shared error
  UI.** They will not hang, but they degrade less informatively than the tabs
  using `tabErrorHTML`. Cosmetic, not fixed here.
