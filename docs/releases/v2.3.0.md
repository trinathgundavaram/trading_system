## Why this release exists

The Real Portfolio tab said "Robinhood not connected. Set ROBINHOOD_USERNAME/
ROBINHOOD_PASSWORD in .env" while `server.log` recorded `live_trader:
Robinhood login OK (session cached)` on every cycle. The credentials were
fine and had been all along. The account NUMBER was the literal string
`${RH_ACCOUNT_NUMBER}`, an exception was thrown on every read, a bare `except`
discarded it, and the UI printed the only failure message it had. Three
separate defects had to line up to produce a message that was wrong in both
its diagnosis and its suggested fix, and each one is closed here.

The second half of the release widens the paper book from $1,000 to $10,000.
At $1,000 the purse itself was the binding constraint rather than the rules:
a $500 position cap meant two positions and the account was fully deployed,
so most BUY signals were declined for insufficient cash instead of on their
merits. The learning data that came out of that is a sample of whatever
arrived first, not of whatever scored best.

## What changed

### Robinhood connectivity — the `${RH_ACCOUNT_NUMBER}` placeholder

- **`${VAR}` is now expanded at the point of USE, not only by the loader** —
  `config_loader:expand_env_refs` — new public function. Phase 0 step 0.2
  moved the account number out of the versioned `config.yaml` and left
  `${RH_ACCOUNT_NUMBER}` behind, expanded by `config_loader`. But
  `server.py:_load_config()` does NOT go through `config_loader` — it reads
  the YAML raw, deliberately, because it also writes the file back and an
  expanded tree round-tripped through `yaml.dump` would bake the secret into
  a versioned file. Every value server.py handed to engine code therefore
  arrived as the literal placeholder.

- **`_account_number()` resolves the reference itself** —
  `engine/live_trader.py:_account_number` — so it is correct no matter which
  loader the caller used. An unresolvable reference now returns `None`
  (= primary account, the documented empty-value behaviour) with a warning,
  rather than sending `"${RH_ACCOUNT_NUMBER}"` to Robinhood as an account
  number.

- **`engine/account_sync.py:_account_number` was a second copy of the same
  two lines** and inherited the same bug. It now delegates to
  `live_trader`'s. Sync must reconcile against the same account the order
  path trades, and two implementations of "which account" is a thing that
  drifts.

- **The probe no longer swallows its exception** —
  `server.py:_robinhood_account_probe` — was `except Exception: read_ok =
  False`. It now logs, and returns `read_error`, which `/api/real/summary`
  and `/api/robinhood/status` both expose. This is the defect that turned a
  five-minute fix into a long one: the real error existed and went nowhere.

- **The UI stops giving advice for a problem that does not exist** —
  `ui/index.html:renderRealPortfolioTab` — the "set your credentials" message
  now appears only when the credentials are actually unset. Otherwise the tab
  prints the real error. Added `escHtml()` and used it on that path, since
  exception text can contain markup.

### Paper book — $1,000 → $10,000

- **`Database.credit_paper_capital(amount)`** — `storage/database.py` — moves
  `starting_cash` and `cash` together in one statement. Capital in is a
  deposit, not a gain: moving cash alone would break `reconcile.py`'s
  `cash == starting_cash - net_buys` invariant AND make a $9,000 contribution
  read as roughly +900% in `snapshot()`'s `total_return_pct`. `realized_pnl`
  is untouched.

- **`scripts/topup_paper_account.py`** — new. Applies the contribution in
  place. The alternative, `reset_paper_account()`, deletes the purse, the
  ledger, the equity curve and every simulated position — the wrong tool when
  the entire reason for raising the balance is to accumulate more data.
  Dry-run by default; refuses to operate on a purse that does not already
  reconcile with its own ledger.

## What this does NOT change

- **The decision function.** No scoring, sizing, entry or exit logic is
  touched. `config_fingerprint` is unchanged at `cc9a149613427f56`, verified
  against v2.2.0's `config.yaml`. Trade history from v2.2.0 and earlier may be
  pooled with this version's.
- **The schema.** No migration. `credit_paper_capital` writes existing columns.
- **The live-execution posture.** `live_execution_enabled: false`,
  `watch_execute: WATCH`, `auto_trade: false`, all unchanged. This release
  fixes a READ path; it opens no gate. `/api/real/sell` remains the only route
  in server.py that can place a real order.
- **Whether the live Robinhood read now succeeds.** The placeholder defect is
  fixed and verified — `_account_number()` returns the real account number
  instead of the literal string. Whether Robinhood then answers is a fact
  about your account and cannot be established from a diff.

## Behaviour you will notice

- The Real Portfolio tab shows an account value and buying power instead of
  "not connected" — or, if the read still fails, shows the actual reason.
- **More paper trades, and larger ones.** This is the point of the release,
  but it means the paper equity curve after 2026-07-26 is not comparable to
  the curve before it on a dollar basis. Percentages remain comparable;
  absolute P&L does not.
- One step up in `paper_equity_history` at the top-up. It raises the running
  peak rather than registering as a drawdown — the mirror-image case, a
  re-seed DOWNWARD, is what caused the v1.3.1 false-drawdown incident.
- `risk.max_daily_loss_pct` (2.0%) now resolves to roughly $200/day against a
  $10,000 basis rather than roughly $20. It remains the tighter of the two
  daily-loss limits and is still what actually binds.
- A new WARNING line if `RH_ACCOUNT_NUMBER` is ever unset:
  `live_trader: account.robinhood_account_number is '${RH_ACCOUNT_NUMBER}'
  and could not be resolved ... falling back to the PRIMARY account.`

## Config changes

| key | old | new | action required |
|-----|-----|-----|-----------------|
| `paper_trading.starting_cash` | `1000` | `10000` | Run `python3 scripts/topup_paper_account.py --apply`. The config value alone does nothing to a live account — `ensure_seeded()` returns early when the purse exists. |
| `risk.max_trades_per_day` | `10` | `30` | None. Throughput for data collection, not a strategy claim. Revisit before EXECUTE. |
| `risk.max_position_size_usd` | `500` | `1000` | None. $1,000 against a $10,000 basis = 10 full-size positions, so `max_positions: 25` stays reachable. |

## Database changes

None. No migration; `schema_migration: none`. `credit_paper_capital()` is an
`UPDATE` of two existing `paper_account` columns.

The data change is operational rather than structural and is applied by an
explicit script, not at startup: `paper_account.starting_cash` 1000 → 10000
and `cash` +$9,000 (864.75 → 9,864.75, with $135.25 deployed in CPRX and AES).
The ledger invariant holds across it by construction.

## Rollback

No schema change, so the previous version reads this database unchanged.

```bash
./scripts/tp promote v2.2.0
```

The paper top-up is data, not code, and does NOT roll back with the version.
To reverse it, run the contribution in the other direction — this restores the
ledger invariant as well:

```bash
python3 scripts/topup_paper_account.py --target 1000 --apply
```

## Known issues carried forward

- **`config_fingerprint` does not cover `risk.max_position_size_usd`.** It
  hashes `position_sizing` and the four risk-level blocks, but of the `risk`
  block only `CONSERVATIVE`/`MODERATE`/`AGGRESSIVE`/`TURBO`. So this release
  doubles the maximum position size without moving the fingerprint, and
  patterns recorded before and after will be pooled as though produced by the
  same strategy. The narrowness is deliberate and documented in
  `learning/pattern_database.py:config_fingerprint`, and widening it now would
  invalidate comparability with every pattern ever recorded — so this is
  logged as a known limitation for a Phase 4 decision, not changed here.
- **`account.robinhood_account_number` reaching engine code as a raw
  placeholder was a class of bug, not one instance.** `_account_number()` is
  fixed, but any FUTURE consumer of a `${VAR}`-bearing config value that is
  reached through `server.py:_load_config()` has the same exposure.
  `config.yaml` currently holds two other references — `ui.auth_token`
  (already immune: §4 made it bypass config.yaml entirely) and
  `notifications.webhook_url` (has a `:-` fallback, so it degrades to empty
  rather than to a literal). A check that no `${` survives into a value handed
  to engine code would close the class.
