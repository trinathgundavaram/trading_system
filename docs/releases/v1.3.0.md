## Why this release exists

Phase 2 is complete. This is the release where "the config says a $500 daily
loss limit" stops being a sentence in a file and becomes true at runtime.

Seven trading days recorded 31 buys against a 10/day cap and reported zero
trades placed every single day, because `daily_stats` was a live-book table
and the only book trading was the paper one. The risk engine answered
`can_trade: True` to every question it was ever asked. Around that sat a
drawdown column written by nothing, a position-opening path with no
transaction around it, a learning table containing rows that are not trades,
a by-ticker UPDATE that matched both books at once, and a portfolio-risk
engine whose limits were measured on names it could not classify and enforced
by nothing.

All ten Phase 2 steps (2.1 through 2.10) are in this tag.

## Version numbering: there is no v1.2.0

`docs/releases/v1.2.0.md` was written and never tagged. Its content — the §4
UI-auth completion across the last eight write routes, and the §12 test
harness — is inside this release. The note is kept, marked superseded, rather
than deleted: a release note that exists should stay interpretable, and
deleting the record of a version that was prepped is exactly the kind of gap
that makes an old changelog useless.

The number is skipped rather than reused. Reusing it would mean two different
trees had at different times been called v1.2.0, which is worse than a gap.

## What this does NOT change

Scoring. No weight, threshold, bucket or stop rule moved. `config_fingerprint`
is unchanged at `cc9a149613427f56`, and that is correct rather than an
oversight — the fingerprint covers the values that map market data to a score,
and none of them moved.

Live execution stays disarmed. `auto_trade: false`, `watch_execute: WATCH`,
`live_execution_enabled: false`, and §32's re-arm gate is untouched.

## Why `decision_function_changed: true` anyway

Two changes alter which trades happen, without altering how a candidate is
scored, and the distinction matters for how you pool history.

**§15 changes a scoring INPUT.** `get_patterns` now filters quarantined rows
for every reader including the live path, so `engine/ev_engine.py` sees a
different sample. The same candidate on the same day can therefore receive a
different EV and a different score. That is a decision-function change in the
strict sense, and it is why `revalidation_required: true`.

**§18 changes SELECTION, not scoring.** A severe portfolio-risk breach now
refuses an entry that previously would have been taken at reduced size. Every
recorded pattern's features-to-outcome mapping is unchanged; what changed is
which candidates become trades at all. Pattern rows from before and after are
individually comparable, but the *set* is subject to a different filter — a
selection effect on the sample rather than a change to the mapping. Worth
stating separately, because "can I pool these?" has a different answer for the
two cases: yes for individual rows, no for anything that reasons about the
population.

Expect `ev_engine` to report insufficient history after migration 007. That is
the true state of the evidence — there is no untainted learning data yet — and
not a regression.

## On the MAJOR classification

`scripts/classify_change.py v1.1.0` returns MAJOR. That is the deliberately
conservative `migrations/` heuristic firing, and this ships as a MINOR bump
on the following reasoning, recorded here so the disagreement is on the record
rather than in a shell prompt.

Migrations 005–008 are additive columns, one partial index and one data
quarantine. No scoring, sizing or exit logic moved. Under the versioning rule
in §35 — the question is whether the mapping from market data to a buy, a size
or an exit moved — the schema changes alone do not justify a major bump.

The genuine decision-function change is §15's EV sample, and its effect is to
*withhold* contaminated evidence rather than to re-weight anything. Pattern
data recorded under v1.1.0 remains poolable with v1.3.0 at the row level.

## Behaviour you will notice

- **Trades will be blocked that previously were not.** The daily budget, the
  loss limit, both drawdown caps and portfolio risk all now bind. With 244 BUY
  signals in eight days from momentum discovery, the correlation and
  concentration limits are expected to fire often. If they fire constantly,
  that is the finding: the screener is producing a single correlated bet.
- `rejected_signals` starts filling, at three stages: `portfolio_risk`,
  `veto`, `threshold`.
- New log lines: `buy skipped - already held, at cap, or insufficient cash
  (lost the race to a parallel worker)`, and `BUY blocked by portfolio risk`.
- The kill switch can now trip by itself, on a realised-loss breach or a
  running-drawdown breach. It only ever flips ON.
- `run.sh` prints a preflight. On failure the UI still starts; the scheduler
  asks first.

## Database changes

| migration | tables | forward | backward |
|-----------|--------|---------|----------|
| 005 | `daily_stats` | `running_drawdown`, `paper_max_drawdown`, `paper_running_drawdown` | drop columns |
| 006 | `positions` | `uq_open_position_per_ticker_book` | drop index |
| 007 | `mae_mfe_data`, `pattern_database` | `data_quality` + four sweeps | drop columns |
| 008 | `rejected_signals` | `would_have_size` | drop column |

Apply with `./scripts/apply_migration.sh migrations/<file>.sql` — **not**
`psql "$POSTGRES_DB" -f`, which resolves to an empty database name on this
project and silently falls back to `$USER`.

All four are additive. v1.1.0 can still read a database these have been
applied to.

**006 will fail on a book that already contains duplicates**, and that failure
is the audit. Run `scripts/inspect_duplicate_positions.py`, decide which row
is real, and `DELETE` the other. Do not close it at an invented price — that
writes a fictional P&L into `paper_trades`, into `daily_stats`, into the
equity curve §11 reads, and into the tables 007 just cleaned.

## Rollback

```bash
./scripts/tp promote v1.1.0
```

Schema is additive, so v1.1.0 reads this database unchanged. Two caveats:

- rolling back re-opens the position-opening race, and `storage/database.py`
  recreates the 006 index on every `Database()` construction, so a rollback
  also means pinning to a build that predates `_ensure_open_position_uniqueness`
- the 007 quarantine marks stay in place and v1.1.0 ignores them, so the
  learning loop would again read the rows this release excludes
