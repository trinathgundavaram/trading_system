## Why this release exists

The Phase 2.5 cutover could not have completed. Its migrations, its purge and
its backup step had all been reasoned about carefully and never executed, and
each of the three was wrong in a way that reading could not have found: a guard
that crashed before reading a row, a purge that deleted the measurement data it
was protecting, and a restore point taken of possibly the wrong database. This
release is what six hours of actually running it produced, plus the two tools
(§40's comparison, Phase 4's harness) the phases after it were waiting on.

## What changed

### The cutover could not have completed

- **012's guard crashed before examining any data** — `migrations/012_mae_mfe_fk.sql` — §C1

  It ran `trade_id !~ '^[0-9]+$'` unconditionally, but `storage/database.py`'s
  `SCHEMA` had since been updated to declare `trade_id INTEGER`. Postgres has no
  regex operator for an integer column, so on any database `init_db()` builds -
  which is every database `tp install` creates - the migration died with
  `operator does not exist: integer !~ unknown`, and step B5 aborted. It also
  could not be re-run after a partial failure, which is precisely what
  `--from B5` exists to allow.

  Two shapes exist and only one had been considered: the LEGACY live database
  (`trade_id TEXT`, `id TEXT` holding uuid4, no FK) and the FRESH one born in
  the post-012 shape. 012 now detects which it faces, applies only what is
  missing, and is idempotent.

- **012 was the only one of 009-012 carrying its own `BEGIN;`/`COMMIT;`**

  `apply_migration.sh` runs every migration under `psql --single-transaction`,
  so the file's `BEGIN` nested inside psql's and its `COMMIT` ended *psql's*
  transaction. Live output: `WARNING: there is already a transaction in
  progress` … `WARNING: there is no transaction in progress`. Harmless in the
  event, because nothing follows the commit point - but the all-or-nothing
  guarantee was defeated for this migration specifically. Transaction control
  now lives in the runner, for all four.

- **The purge deleted the excursions §21 derives from** — `scripts/repair_test_damage.py` — §49

  `ticker_collision` deleted every row whose `trade_id` resolved to no position.
  But positions are deleted *routinely and by design* - `reset_paper_account()`
  removes every simulated one - so that is the normal fate of a real excursion
  row, not evidence of anything. On the live table it matched all 30 rows, of
  which 7 carry genuine excursion values (DLR, ADPT, USB, SHEL, BMY, SGRY,
  ORIC).

  `migrations/012` had already decided what an orphan means, and chose
  `ON DELETE SET NULL` over CASCADE for exactly this reason: *"The maximum
  adverse excursion of a trade that happened is a fact about that trade, and it
  stays true after the position row is gone."* The purge was contradicting the
  migration beside it. Split into `ticker_mismatch` (delete - resolves to a
  position of a different ticker, unrepairable) and `orphan_trade_id` (SET NULL,
  row kept), with the unlink running after the deletes so a row that is both
  junk and orphaned still goes.

- **The purge report's headline number could be read as "all of it"**

  It printed a SUM of overlapping predicates - `30 raw` against a 30-row table -
  which invites exactly one conclusion, and it was wrong: 7 of those rows match
  no delete predicate. It now computes and prints the union:
  `ACTUALLY DELETED 23 of 30 rows (7 kept)`.

- **The `trades_placed` advice was stale prose arguing to corrupt a correct figure**

  Three hardcoded sentences - "Current value is 10, so 3 test increments. 7 is
  the likely correct value" - true when written. By the time anyone read them
  the value was 6 and the surviving ledger held 6 rows. Now computed from the
  ledger, and when they agree it says so.

- **B2 backed up the wrong database, or none** — `scripts/phase2_5_cutover.sh`, `scripts/tp`

  It passed `phase2_5_cutover` as a label, but `tp backup` takes a VERSION and
  resolves it through the registry, so it died on `unknown version`. Underneath
  that was the quiet one: with a `PRIMARY` set, a bare `tp backup` dumps the
  primary version's database, which need not be the one B3-B7 modify. A restore
  point for the wrong database is worse than none, because it is believed.
  `tp backup` gains `--db` (verbatim, bypassing the registry) and `--label`
  (names the archive - an archive of forty `working_<ts>.sql.gz` files cannot
  answer "which one is from before the cutover"). B2 asks
  `storage/database.py` which database it resolves to.

- **`assess_test_damage.py` queried a column that has never existed**

  `monitoring_alerts.created_at`; the column is `triggered_at`. The alerts
  section reported `ERR` and then silently nothing, every run.

### Operational

- **`service.sh restart` raced its own bootout** — `scripts/services.py` — §45

  `launchctl bootout` returns when the request is *accepted*, not when the job
  is gone, so `bootstrap` landed while the label was still registered:
  `Bootstrap failed: 5: Input/output error` / `Try re-running the command as
  root`. Root would not have helped. `start` now polls until the label leaves
  the domain, skips a pointless bootout when nothing is loaded, and `stop`
  waits too - so anything following `stop` is not racing a scheduler still
  holding connections.

- **`tp` allocated ports the registry thought free and the OS did not** — `scripts/tp` — §38

  `registry_add()` avoided ports claimed by other *managed* versions, which says
  nothing about `./run.sh --ui` or anything else on the machine. It now tests
  whether the port can be bound.

- **`TP_PG_POOL_MIN` / `TP_PG_POOL_MAX`** — `storage/database.py`

  The pool was hardcoded 2-20, so a server that cannot give out two connections
  failed inside `Database.__init__` as "server closed the connection
  unexpectedly" - which reads like the server died. Defaults unchanged.

### New tools

- **`scripts/rehearse_cutover.py`** — runs the whole migration sequence against a
  throwaway database in both shapes, asserting what the cutover assumes: that
  010 and 012 refuse while contamination is present, that both shapes converge,
  that 012 is re-runnable, and that deleting a position NULLs the excursion row
  rather than cascading it. Refuses to open the live database or any `tp_v*`
  version database. **This is what found the 012 defect.**

- **`scripts/compare_versions.py` (§40)** — deferred since v1.3.0, and named in two
  places as the thing that makes a claim measurable. It treats the comparison as
  two questions decided by the config fingerprint: same fingerprint and
  different numbers is a REPRODUCIBILITY FAILURE; different fingerprint and
  identical numbers means the change was INERT. Trades are compared as a set
  keyed on (ticker, entry date), because two runs can agree on count, win rate
  and profit factor while disagreeing about which trades those were.

- **`scripts/phase4_recalibrate.py` (§19-§21)** — the recalibration machinery,
  deliberately not the numbers. `assess` refuses a sample that is too small
  (150, reusing `learning.min_trades_before_bayesian`), too short (90 days),
  missing the §48 epoch, or thin on linked excursions - and names every feature
  that never varies, which is the placeholder problem in numbers rather than
  prose. `propose` derives weights from measured rank correlation and writes a
  proposal file. `receipt` writes the §32 validation receipt that
  `engine/live_trader.py` has looked for since Phase 1 and never found.

- **`scripts/diagnose_drawdown.py`** — read-only. Whether a drawdown is real or an
  accounting event, decided by the accounting identity rather than a threshold:
  since `total_value = cash + market_value`, market movement leaves cash flat, a
  buy or sell moves both legs opposite and cancels, and only a balance change
  leaves cash moving unmatched. Then rebases the series - the arithmetic §48
  performs - because measuring "from the last jump" misses a transient spike,
  where one bad balance sample becomes the all-time peak forever.

## What this does NOT change

The decision function. Nothing here touches scoring, sizing, entry or exit
logic; no config value a rule reads has moved; `config_fingerprint` is unchanged
at `cc9a149613427f56`. Trade history remains poolable across this tag.

`phase4_recalibrate.py` proposes and applies nothing - a test asserts the script
contains no yaml writer, because that property is worth more than the intention
behind it.

## Behaviour you will notice

- `service.sh restart` takes up to a few seconds longer, and works.
- `tp run` on a newly installed version no longer dies on `[errno 48]`.
- The purge keeps 7 excursion rows it used to delete, with `trade_id` NULL.
- `assess_test_damage.py` prints alerts instead of `ERR`.

## Database changes

No new migration. `migrations/012` is corrected and made idempotent; a database
that already applied it is unaffected, and re-applying is a no-op that says so.

## Validation

Full suite: 366 in the sandbox, **457 against Postgres** including the 92 that
normally skip. The cutover's B9 step ran them green on the release machine.
`rehearse_cutover.py` clean on both shapes. No validation receipt is claimed -
live execution remains disarmed.

## Known issues carried forward

- **§48's reset, §52/§53/§55's numbers.** The cutover has been run; the caps
  still need elapsed time. B8 declines to recommend below 10 days of curve.
- **`max_daily_loss_pct` and `max_intraday_drawdown_pct` are both 2.00%**, so the
  drawdown gate fires first in essentially every scenario and the realised
  daily-loss limit - the only one that escalates to the kill switch - is
  effectively unreachable. A decision, not a bug, but make it deliberately.
- **Phase 4 remains unstarted.** The harness exists; the sample does not.
  `pattern_database` holds 84 patterns, 44 closed, against a floor of 150.
- **`/api/config` still strips YAML comments** on save (needs `ruamel.yaml`).
- **Placeholder indicators** - ADX, CMF, market breadth, anchored VWAP, industry
  RS, unusual options, VIX percentile - remain 0.0 defaults. `phase4
  assess` now names them.
