## Why this release exists

Phase 1 of the 2026-07-24 remediation plan: contain the risk that can cost real
money before Phase 2's controls exist. Four holes, none of them in the scoring
or exit logic. A dashboard gating the kill switch and real-money sells was
reachable from every device on the LAN behind a five-character token. Eight
imported Robinhood holdings worth roughly $42,000 sat in the `positions` table
with live ATR stop machinery attached, reachable by every automated exit path,
their stops sized for $100 engine entries. The startup banner told an operator
the platform could not place real orders, which had been untrue since 16 July.
And the Bayesian learning gate was open on 23 closed patterns, every one
produced under the stop bug removed on 20 July.

## What changed

### §4 — UI auth surface (E-3)

- UI binds `127.0.0.1` by default; `TP_UI_HOST` is an explicit override that
  prints a four-line red warning when used — `main.py:run_ui`
- Nine inline `x_auth_token != _auth_token()` checks replaced by one
  `require_token` FastAPI dependency — `server.py`
- `hmac.compare_digest` instead of `!=`. A plain compare short-circuits on the
  first differing byte and leaks the token to anyone who can time a response
- Per-client throttle: 5 failures in 5 minutes → 429 for 15 minutes. The
  throttle runs *before* the comparison, so a brute-forcer who would have
  succeeded on attempt six does not
- The token now resolves through `storage/secrets.py` (environment → `.env` →
  Keychain), never `config.yaml`. **This closes a live hole opened by Phase 0
  step 0.2:** `server.py` reads `config.yaml` raw, without `config_loader`'s
  `${VAR}` expansion, so `_auth_token()` had been returning the literal string
  `${UI_AUTH_TOKEN}` — anyone sending that as a header would have
  authenticated. Regression test: `tests/test_ui_auth.py`
- Misconfiguration now 503s rather than authenticating. An expected token of
  `''` compares equal to a blank header

### §5 — SYNC/SEED quarantine (R-5)

Three independent layers, because one guard on a $42,000 exposure is a single
point of failure:

- Layer 1 — `Database.get_managed_positions()` / `is_managed()` —
  `storage/database.py`. `MANAGED_EXCLUDED_MODES` is the canonical constant
- Layer 2 — `SellRulesEngine.evaluate()` returns `should_sell=False` for
  SYNC/SEED before reading any config — `rules/sell_rules.py`
- Layer 3 — `execute_sell_live()` refuses an automated sell and logs a
  `unmanaged_sell_blocked` UI event — `engine/live_trader.py`
- Call sites switched to the managed query: the price-watch loop
  (`scheduler.py`), Loop B (`engine/position_management.py:run_loop_b`), and
  rotation victim selection (`engine/rotation.py`, which also keeps its
  existing in-loop check — rotation places a real market sell on the victim,
  so belt *and* braces is warranted there)
- `migrations/002` preserves and then NULLs the stop machinery already sitting
  on those rows (KMB in `TREND_FOLLOWING`, RVI in `PROFIT_PROTECT`, SMFL with a
  stop exactly equal to its entry)
- `scripts/audit_stops.py` reports zero-distance, missing and prematurely
  advanced stops. It deliberately does **not** use the plan's
  `current_stop_price >= entry_price` predicate, which flags every healthy
  position whose stop has legitimately advanced past entry — a report that
  cries wolf is a report nobody reads

### §2 — Validation receipt (R-4)

- `is_live_mode()` gains a fourth gate: a passing validation receipt no more
  than 30 days old, written by `run_backtest.py` only when a run clears the
  §23 go/no-go bar — `engine/live_trader.py:_validation_current`
- Fails closed on a missing, failed, stale or corrupt receipt
- No receipt exists yet, and that is correct: §23 lands in Phase 4. Live
  execution is now blocked by code, not by intention

### §6 — Runtime posture banner (E-4)

- `storage/banner.py` — resolves posture from `live_trader`'s own gate
  functions, so it cannot disagree with behaviour
- Printed by `main.py` (both modes) and logged by `scheduler.py` at startup;
  returned as `execution_posture` from `/api/status`
- The five false claims are gone. Four docstrings now describe what their
  module *does* rather than what the deployment happens to be configured to do
  — `main.py`, `server.py`, `engine/live_trader.py`, `engine/paper_trader.py`,
  `rules/execution_quality.py`

### §17 — Learning freeze and pattern provenance (T-9)

- `learning.bayesian_enabled: false` — a hard gate independent of any count,
  checked by `learning_frozen()` at all three write paths: `propose_update`,
  `apply_bucket_weight_to_config` and `propose_as_challenge`. Fails closed when
  the key is absent: an absent flag on a safety gate is not consent
- `min_trades_before_bayesian: 10 → 150`. Six weighted buckets and ~60 rules
  cannot be fitted from 23 observations; the parameter space exceeds the sample
- `min_pattern_recorded_at: 2026-07-25T00:00:00`, applied via
  `Database.get_closed_patterns()` in `engine/learning_loop.py`
- New `LearningFrozen` exception, distinct from `ShadowValidationRequired` —
  different problems with different remedies
- `migrations/003` adds `engine_version` and `config_fingerprint` to
  `pattern_database`; `PatternDatabase.record_entry(cfg=...)` stamps every new
  row. This makes the Phase 4 recalibration self-partitioning: the moment the
  weights change, every later pattern is distinguishable from every earlier one

## What this does NOT change

- **No scoring, sizing, threshold or exit logic was touched.**
  `rules/swing_buy_rules.py`, `engine/position_sizing.py`,
  `engine/stop_state_machine.py` and `rules/exit_scorer.py` are untouched.
  `decision_function_changed: false`, and pattern data from v1.0.0 remains
  poolable with v1.0.1
- The §17 cutoff is applied to the **learning path only**. The EV engine's
  pattern matching (`engine/ev_engine.py` → `find_similar_trades` →
  `get_patterns`) still sees every closed pattern, because filtering it would
  change live scoring. `get_patterns()`'s defaults are unchanged for exactly
  that reason; §15 (Phase 2) extends the filter to every learning read
- `risk_level` stays `TURBO`. §20 (Phase 4) re-derives the whole ladder
- Manual real sells still work on SYNC positions via `/api/real/sell`. The
  layer-3 refusal is gated on `require_auto_trade`; being unable to exit a real
  position by hand would itself be a risk
- The kill switch still does not block sells. That reasoning was correct and
  is unchanged — closing the three arming gates is what blocks both sides
- Phase 2's risk controls are **not** in this release. Paper trades still do
  not increment the daily budget (R-1), the daily-loss limit is still fed zero
  (R-2), and the automatic kill switch is still never called (R-3)

## Behaviour you will notice

- The dashboard is no longer reachable from other devices. Use
  `ssh -L 8080:localhost:8080 you@mac` or Tailscale — both give transport
  encryption a bearer token over plain HTTP cannot
- The browser will ask for the auth token again; it is a new 32-character value
- Startup prints four new lines. Today they read:
  `EXECUTION: PAPER - no real orders possible` /
  `validation: no validation receipt - run the backtest gate first`
- SYNC holdings disappear from Loop B. The Positions tab will show them without
  a stop or health score — that is the intended state, not missing data
- No learning run will trigger until 150 patterns recorded on or after
  2026-07-25 accumulate. Expect `Bayesian learning is frozen` in the log
- `LIVE BLOCKED - <reason>` appears at most once per 5 minutes per reason, and
  immediately when the reason changes

## Database changes

Two migrations, both additive, both with backward SQL in the file.
`Database.init_db()` also applies the schema half idempotently
(`_migrate_phase1_columns`), so a fresh database converges without them.

- `002_quarantine_unmanaged_positions.sql` — adds `quarantined_stop_price`,
  `quarantined_stop_state`, `quarantined_at` to `positions`; copies then NULLs
  the stop state on open SYNC/SEED rows. **The data half is not repeated in
  code — run this file.**
- `003_pattern_provenance.sql` — adds `engine_version`, `config_fingerprint` to
  `pattern_database`; backfills `'pre-provenance'`; two indexes

```bash
psql "$POSTGRES_DB" -f migrations/002_quarantine_unmanaged_positions.sql
psql "$POSTGRES_DB" -f migrations/003_pattern_provenance.sql
python3 scripts/audit_stops.py    # expect: no impossible or missing stops
```

`rollback_safe: true` — v1.0.0 reading this database sees columns it ignores,
and NULL stops on rows it must not have been exiting anyway.

execution blocked. What was run:

- `tests/test_live_arm_gate.py` — 12 tests, receipt gate and banner

- `tests/test_learning_freeze.py` — 18 tests, freeze + fingerprint + shipped config

Two pre-existing tests were updated because they asserted the *old* behaviour:
`test_is_live_mode_gates` (the `enabled` fixture now supplies a receipt) and
`test_confirm_phrase_required_to_enable` (the handler no longer takes an
`x_auth_token` argument). A new `test_is_live_mode_without_a_validation_receipt`
covers the case the first one used to.

## Rollback

```bash
./scripts/tp promote v1.0.0
```

The schema is additive, so v1.0.0 reads this database unchanged. To restore the
quarantined stops, run the commented BACKWARD block in
`migrations/002_quarantine_unmanaged_positions.sql` — but note that doing so
re-arms exit machinery on real holdings, which is the defect this release
exists to close.
