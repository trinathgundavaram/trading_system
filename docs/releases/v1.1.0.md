## Why this release exists

`scripts/audit_stops.py`, added in v1.0.1, immediately found what it was built
to find. AES was holding entry 14.8050 with `current_stop_price` 14.8095 and
`stop_state` `INITIAL_RISK` — a position reporting "no protection earned yet"
while carrying a stop above its own entry price.

The stop was right. `BREAKEVEN` had set it to
`entry + risk_per_share × breakeven_lock_r`, and `should_advance()` then
correctly refused to widen it when price fell back. The label was wrong:
`calculate()` re-derived its stage from the *current* `profit_r` on every
cycle, with no memory of what the trade had already achieved. Price dips back
under `breakeven_r`, the stage silently reverts, and from then on the row's
state and its price describe two different positions.

## What changed

### engine/stop_state_machine.py

- `calculate()` is now a thin wrapper: `_calculate_raw()` computes the stage
  this cycle's numbers imply, and `_apply_stage_ratchet()` floors it at the
  stage the position has already reached
- `_STAGE_RANK` orders `INITIAL_RISK < TRADE_CONFIRMING < BREAKEVEN <
  PROFIT_PROTECT < TREND_FOLLOWING`
- `THESIS_BROKEN` is deliberately outside the ranking. It is an emergency that
  must fire from any stage, so it is never suppressed by the ratchet and is
  never treated as a stage that can be regressed *from*
- A ratcheted result returns `max(candidate_price, current_stop_price)` — which
  is what `should_advance()` already enforced independently, so no stop moves
  that was not already going to move
- `_calculate_raw()` is intentionally public-ish and importable so the test
  suite can prove the ratchet is what fixes the regression, rather than some
  incidental drift in the stage arithmetic

## On `decision_function_changed: false`, against a `MAJOR` classification

`scripts/classify_change.py` reports **MAJOR**, because
`engine/stop_state_machine.py` is on its decision-function file list. That
list is a heuristic over paths; this note is the place to answer it with
analysis. `release.sh` will warn and prompt — continuing is correct here, and
this section is the justification.

All four consumers of `stop_state` were enumerated:

| Consumer | Effect | Can it change a trade? |
|---|---|---|
| `rules/sell_rules.py:123` | sets `stop_urgency` on the `SellResult` | No — `urgency` is read only by `engine/packet_builder.py:453`, for display |
| `engine/packet_builder.py:186` | prints the state in the prompt file | No |
| `engine/position_management.py:288` | `THESIS_BROKEN` → urgent exit | No — the ratchet only moves a stage *up*, and `THESIS_BROKEN` is exempt, so this branch is reachable in exactly the cases it was before |
| `engine/position_management.py:311` | HOLD vs STOP ADVANCEMENT label | No — both are `priority: 4`, `urgent: False`, and `scheduler.py` executes only on `priority_action["urgent"]` |

The stop *price* is untouched: `max(candidate, current)` is identical to what
`should_advance()` already produced. No entry, exit, size or threshold moves.

**Therefore trade history from v1.0.0 and v1.0.1 remains poolable with this
version**, and `config_fingerprint` is unchanged at `cc9a149613427f56` — this
release edits no decision-relevant config key, so the v1.0.1 validation
receipt (when one exists) is not voided.

It is a **minor** bump rather than a patch because observable behaviour does
change: log lines, the prompt file, the Positions tab and `/api/status` will
all now show the held stage instead of a reverted one.

## What this does NOT change

- No stop price, on any position, in any state
- No entry logic, no sizing, no thresholds, no exit scoring
- Nothing in Phase 2's scope: R-1, R-2 and R-3 remain open
- `scripts/audit_stops.py` still reports `STATE_REGRESSED`. It is now a
  detector for rows written *before* this release rather than for an active
  defect, and should fall silent as Loop B rewrites each position's state

## Behaviour you will notice

- A position that reached breakeven and then pulled back keeps reporting
  `BREAKEVEN` rather than flipping to `INITIAL_RISK`
- Its exit, if the stop is hit, is labelled `normal` urgency instead of
  `urgent` — which is the honest description of a breakeven-protected exit
- Loop B logs `STOP ADVANCEMENT` where it previously logged `HOLD` for these
  rows
- `stop_reason` on a ratcheted cycle reads
  `"<STAGE> held (stage ratchet): the current reading would imply <X>, but a
  stage a trade has reached does not revert while its stop stands."`
- Existing rows heal on their next Loop B pass; no backfill is needed

## Database changes

None. `schema_migration: none`.

Existing `positions.stop_state` values are stale rather than wrong-shaped —
whatever a row currently records is taken as "the stage reached", and the
ratchet floors at it from there. A row stuck at `INITIAL_RISK` with a stop
above entry (the AES case) will not retroactively become `BREAKEVEN`, but it
can no longer regress *further*, and it advances normally on the next cycle
where its profit warrants it.
