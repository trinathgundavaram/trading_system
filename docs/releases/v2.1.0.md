## Why this release exists

Phase 3 of the remediation plan (§41–§47). It is deliberately sequenced BEFORE
recalibration, not after.

Phase 4 is a large change to the decision function whose entire justification
is a measured before-and-after. That measurement is only worth something if
both versions compute indicators identically. §41 found that they might not:
`engine/ticker_analyzer.py` falls back from `pandas_ta` to a hand-rolled engine
when the import fails, and nothing tells you which is active. Three operating
systems × several Python versions × unpinned numeric libraries is a matrix in
which the same bars produce different indicator values, therefore different
scores, therefore different trades — with no error and no log line.

So this release is not about convenience. It is about whether a score computed
on one machine means the same thing as a score computed on another.

Along the way it fixes three genuine safety holes that only existed off macOS,
one of which was the hard-kill supervisor.

## What changed

### The three that were safety-critical

**Hang protection now works on every OS** — `engine/cycle_supervisor.py` — §43.2

The supervisor exists because the scheduler silently stopped firing for five
hours on 22 July. Its mechanism — put the child in its own process group,
SIGKILL the group — used `os.killpg`, `os.getpgid`, `signal.SIGKILL` and
`start_new_session=True`, none of which exist on Windows. The module raised
`AttributeError` at import there, which means the platform had **no hang
protection at all** on that OS.

POSIX keeps the process-group path: it is atomic and catches a grandchild that
re-parented away, which a tree walk cannot promise. Windows gets a psutil tree
walk. Two limitations are stated rather than hidden — a process spawned during
the walk can be missed, and a descendant already re-parented to a system
process is unreachable — because both are still enormously better than nothing.

**Secrets no longer degrade to plaintext off macOS** — `storage/secrets.py` — §44

`security add-generic-password` exists only on macOS. On Linux or Windows the
keychain tier returned `''` silently and everything fell through to the
environment, which in practice means a file on disk — the exact outcome §3 and
§39 exist to prevent.

Now `keyring`, which wraps the native store on each platform: Keychain,
Windows Credential Locker, Secret Service, or `keyrings.cryptfile` on a
headless box. Resolution order is environment → `.env` → keyring, and the
environment being FIRST is the load-bearing part: reverse it and containers
become impossible. `TP_STRICT_SECRETS=1` drops the plaintext `.env` tier
entirely; it is opt-in only because the running installation has a populated
`.env` today and ignoring it silently would look like a credential outage
rather than a policy change.

**Background services exist on every OS** — `scripts/services.py` — §45

`service.sh` was `launchctl bootstrap`, `~/Library/LaunchAgents` and plist XML
from top to bottom. Everywhere else the scheduler ran in a foreground terminal
and died with the window — which is precisely the failure `service.sh` was
written to fix on macOS.

Three implementations behind one interface: launchd, systemd user units,
Windows Task Scheduler. Every hard-won macOS detail is carried across and
commented with the incident that produced it — the 4096/8192 open-file limits
from the 2026-07-17 fd exhaustion, the full installing-shell PATH for npx/uvx
subprocesses, `caffeinate -i`, and the §38.5 per-version label suffix.
`service.sh` survives as a shim so `tp promote` and muscle memory keep working;
the original is `service.launchd.sh.bak`.

Honest caveat, restated from the plan: Windows Task Scheduler is the weakest of
the three. No real supervision, primitive logging, and `ONLOGON` means nothing
runs when nobody is logged in. If Windows is your main platform, run the
containers under WSL2 and get systemd semantics instead.

### The container — §42

`Dockerfile`, `docker-compose.yml`, `.dockerignore`, `scripts/healthcheck.py`,
`scripts/build_version.sh`.

The image pins the OS, the Python build, every wheel and the timezone database.
Two build-time assertions matter more than they look:

- `import pandas_ta` — failing the BUILD is infinitely better than discovering
  at runtime that this image fell back to `ta_fallback.py` and computed scores
  comparable with nothing (§13).
- `ZoneInfo('America/New_York')` — a slim image has no zone database, and the
  failure mode is not an exception but a silent UTC fallback that shifts every
  market-open check by four or five hours.

The UI publishes on `127.0.0.1` only. `TP_UI_HOST=0.0.0.0` inside the container
looks like it contradicts §4 and does not: the bind that matters is the host
side of the mapping. Writing `8080:8080` would publish it to the whole network
and, on Docker, bypass most host firewalls.

`TP_FORCE_PAPER` defaults to 1. A version that has not been explicitly promoted
cannot arm live execution whatever its committed config says (§38.4).

**A skewed clock refuses to trade** — `scheduler.py` — §42.4. Docker Desktop's
VM clock can lag the host badly after a laptop sleeps, and this process decides
whether the market is open and when a stop was hit. Above 120s of skew the
cycle aborts and the block is recorded. Compared against an HTTP `Date` header:
no NTP client in the image, one cheap request, cached five minutes. A `None`
result — no network — proceeds, because converting a network blip into a
trading outage is a worse trade than the risk it guards against.

### The split — §47

The tension is real: OS-independence argues for a container, but the features
used daily — notifications, the clipboard, keeping the Mac awake, starting at
login — are exactly what a container cannot reach. Picking one and losing the
other is the wrong trade.

**The engine states what happened; the host decides how you find out.**
`scheduler.py`'s `notify_buy_signal()` / `notify_urgent_exit()` calls became
`log_ui_event()` writes. `storage/database.py` fires a transactional
`pg_notify` alongside the INSERT — transactional matters: the agent can never
be told about an event that was rolled back. `scripts/tp_agent.py` LISTENs,
and does the four things a container cannot: native notifications, the
wakelock, reading the host keyring, and starting the stack.

That agent is ~150 lines and is now the entire OS-specific surface of the
platform. Porting to another OS means porting that file, and §43 already wrote
every alternative branch in it. It contains no trading logic and makes no
decisions: if it dies, the engine keeps running and you stop getting popups.

A fallback is built in and is not optional. If `TP_HOST_AGENT` is unset — a
native install with no agent — the scheduler also delivers directly, so nobody
silently stops receiving notifications the day this ships.

**Clipboard and file-open moved into the browser** — §47.5. `/api/prompt/copy`
shelled out to `pbcopy` on the server, which assumed the server process and the
person clicking the button were the same machine. That was already false over
an SSH tunnel. `navigator.clipboard` and a new `/api/prompt/raw` fix the
container case and make the feature better on macOS too — it now works
remotely, from a phone, and through a tunnel.

### Everything else

- `storage/platform_support.py` — every OS-specific call in one file, each
  degrading rather than raising. `main.py`'s clipboard and open now route
  through it — §43.1
- `engine/notifications.py` — an ordered transport chain (desktop → webhook →
  log). `log` is last and always succeeds, so a notification is never silently
  dropped; the previous code logged a warning and moved on, which on a headless
  box was every time. The webhook transport is the one that reaches a phone —
  §43.3
- `scripts/tp` rewritten in Python — `rm -P`, `shasum` and `sed -i ''` are all
  BSD-only, and `TP_ROOT` now respects `%LOCALAPPDATA%` and XDG rather than
  putting gigabytes in a roaming profile. Bash kept as `scripts/tp.sh.bak` —
  §46.1
- `scripts/bootstrap.py` — what is missing on this machine, with the install
  command for this OS — §46.2
- `requirements.txt` — `psutil`, `keyring`, `keyrings.cryptfile`, `tzdata`
- `tests/test_phase3_portability.py` — 49 tests, including a lint that fails if
  a macOS-only binary appears anywhere in the engine

## What this release does NOT claim

**The Phase 3 exit criterion has not been run.** It is not a code change and
cannot be satisfied by one:

    ./scripts/build_version.sh v2.0.0
    ./scripts/build_version.sh v2.1.0
    TP_VERSION=v2.0.0 TP_UI_PORT=8080 \
      docker compose --env-file .env.runtime -p tp-v2-0-0 up -d
    TP_VERSION=v2.1.0 TP_UI_PORT=8081 \
      docker compose --env-file .env.runtime -p tp-v2-1-0 up -d
    # run the same backtest window in both; the shared code paths must
    # produce identical numbers

**Read the comparison carefully, because v2.0.0 and v2.1.0 are not a clean
pair.** v2.0.0 carries §53, which moved a decision. So the two builds are
*expected* to differ wherever portfolio risk sizes or blocks a position — that
is the §53 change doing its job, not a pinning failure. What must match is
everything upstream of it: the indicator values and the raw scores, which
neither release touched. If those diverge, the pinning is still loose.

A cleaner test, if you want one, is to build v2.1.0 twice on two different
machines and diff the same backtest. That isolates the property this phase
actually claims, with no decision change in the way.

Either way: until this has been run, the reproducibility property above is a
design intention, not a measured fact.

Two other things are deliberately deferred:

- The `FROM python:3.12-slim` line is pinned by tag, not by digest. The
  `docker inspect` command to convert it is in the Dockerfile. The build works
  either way; the 2029 guarantee does not.
- Nothing yet lifts `ev_engine`'s `p_stop_loss` onto the §48–§55 excursion
  table. That is Phase 4 and will be its own declared decision change.

## Where this is worse than native, stated honestly

- **Docker Desktop becomes a dependency.** If it is not running, nothing runs.
  Mitigated by the launchd wait loop and the container health check, but it is
  a real new failure mode.
- **Clock drift after sleep.** The §42.4 guard is part of this architecture,
  not a nice-to-have.
- **Debugging gains a layer.** `docker compose exec` instead of attaching
  directly. Keep a native venv for development; the code is identical.
- **Roughly 2 GB of RAM** for the Docker VM on a Mac. Comfortable on 16 GB,
  noticeable on 8 GB alongside Postgres and a browser.

None of these outweighs the reproducibility gain, but adopt the approach
knowing them rather than discovering them.

## Upgrade steps

    pip install -r requirements.txt          # psutil, keyring, tzdata
    ./scripts/tp secrets import              # mirror .env into the OS keyring
    ./scripts/bootstrap.py                   # confirm this machine is complete
    ./service.sh install                     # re-install services via the new manager

Optional, for notifications that reach you away from the machine: set
`NOTIFY_WEBHOOK_URL` (e.g. an `ntfy.sh` topic).

## Rollback

Safe. No schema migration, no config fingerprint change on any key a rule
reads. `git checkout v2.0.0` restores the previous behaviour; `service.sh`,
`scripts/tp` and `engine/notifications.py` all revert to working macOS-only
implementations, and `service.launchd.sh.bak` / `scripts/tp.sh.bak` are kept in
the tree for comparison.
