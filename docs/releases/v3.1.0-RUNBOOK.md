# v3.1.0 release runbook

Everything below runs on your machine. Prepared 2026-07-26.

Prep already done: `CHANGELOG.md` has the `## [3.1]` heading `release.sh`
greps for, `docs/releases/v3.1.0.md` exists and is filled in, and the code
changes are in the working tree. `release.sh` stamps `VERSION` itself — do not
edit it by hand.

---

## 0. Clear the stale git lock

```bash
cd ~/trading_platform
lsof .git/index.lock 2>/dev/null || rm -f .git/index.lock
```

`lsof` prints nothing and exits non-zero when no process holds the file, so the
`||` only fires when it is genuinely unheld. If `lsof` *does* print something,
stop — a real git process is running.

## 2. Cut the release

```bash
./scripts/release.sh minor
```

This is the whole release. It will, in order:

1. refuse if the tree is dirty or you are not on `main`/`release/*`
2. **run `pytest tests/ -q` as a hard gate** — see the warning below
3. run `check_deps.py`, `check_config_secrets.py`, `gitleaks` if installed
4. run `verify_phase1.py --release` and `verify_phase2.py` (blocking)
5. run `reconcile.py` (non-blocking — expect findings, see below)
6. compute `v3.1.0` from `v3.0.0`, cross-check the level against the diff
7. require `docs/releases/v3.1.0.md` — already written
8. require the `## [3.1]` CHANGELOG heading — already written
9. stamp `VERSION`, commit, `git tag -a v3.1.0 -F docs/releases/v3.1.0.md`
10. cut branch `release/3.1`
11. `git push --follow-tags`

### Before you run it — check where pytest points

`release.sh`'s own comments record a 2026-07-25 incident in which the suite ran
against the **live database**. Confirm the test config targets a scratch DB:

```bash
grep -rnE "POSTGRES_DB|DATABASE_URL|trading_platform" pytest.ini tests/conftest.py 2>/dev/null
```

If anything there resolves to your real `trading_platform` database, fix that
before releasing. This is the one step worth being slow about.

### Expect `reconcile.py` to report findings

It is non-blocking by design. It reads the state of the *data*, not the code,
and your book currently has a genuine cross-account discrepancy (CLF, bought in
the primary account). That is pre-existing, it is exactly what this release
makes visible, and it is not a reason to hold the tag. Do **not** resolve it by
writing corrective rows at invented prices.

## 4. Deploy

```bash
./scripts/tp install v3.1.0
./scripts/tp list                 # confirm port + database assignment
```

Then promote it, which is what makes it the version allowed to arm:

```bash
./scripts/tp promote v3.1.0
```

Restart the services so the new `server.py` is actually running — the UI HTML
is re-read per request, but Python is not:

```bash
./service.sh restart
```

Verify the deploy took, rather than assuming:

```bash
curl -s localhost:8080/api/real/summary | python3 -m json.tool \
  | grep -E '"(account_value|cash|holdings_value)"'
```

`cash` and `holdings_value` are new in v3.1.0. If they are absent, an old
process still holds the port:

```bash
lsof -ti:8080 | xargs kill
```

The four new `positions` columns are created automatically on first start by
`_add_column_if_missing()`. No migration step.

---

## What deploying does NOT do

**It does not arm live trading.** All five gates are unchanged and independent:
`TP_FORCE_PAPER` unset, `trading.live_execution_enabled`, a current validation
receipt, `trading.watch_execute: EXECUTE`, and `trading.auto_trade: true`. Your
current posture is `NO REAL ORDERS POSSIBLE` and this release does not move it.

A backtest receipt is **not** required for this release —
`decision_function_changed: false` and the config fingerprint is unchanged, so
the existing receipt is unaffected. You do need one before arming, and the
Execution Posture panel currently reports `no validation receipt - run the
backtest gate first`.

---

## Rollback

Schema changes are additive, so v3.0.0 can still read a v3.1.0 database. No
data step:

```bash
./scripts/tp promote v3.0.0
./service.sh restart
```

## Separately: the test-session P&L

Not part of the release, and safe to do before or after:

```bash
pg_dump trading_platform > ~/tp-backup-$(date +%F).sql
psql trading_platform -f scripts/cleanup_test_pnl.sql
```

Zeroes `realized_pnl`/`winning_trades` for 2026-07-24 only, after copying the
originals to `daily_stats_pnl_backup`. Deletes no trade, position or history
row. The undo statement is printed at the end.
