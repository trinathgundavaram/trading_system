# v3.3.2 Release Notes

**Date**: 2026-07-27  
**Priority**: Minor (Service Startup Fixes)  
**Rollback**: `./scripts/tp promote v3.3.1`

---

## Summary

Fixes launchctl bootstrap failures ("Input/output error", exit 5) that prevent service startup on macOS after reinstalls or persistence layer corruption. Implements automatic retry logic that transparently handles stuck registrations without manual intervention.

---

## The Problem

After promoting v3.3.1 or running service cleanup, `launchctl bootstrap` would fail with:

```
Bootstrap failed: 5: Input/output error
Try re-running the command as root for richer errors.
```

This left all services (scheduler, ui, maverick) unable to start and required manual commands:

```bash
launchctl bootout gui/501/com.tradingplatform.v3.3.1.scheduler
rm ~/Library/LaunchAgents/com.tradingplatform.v3.3.1.scheduler.plist
sudo launchctl bootstrap gui/501 ~/Library/LaunchAgents/com.tradingplatform.v3.3.1.scheduler.plist
```

**Root cause**: launchctl's persistence layer (plist registry) can become corrupted after:
- Multiple rapid service installs in one session
- Service uninstall followed by immediate reinstall
- Stale registrations surviving reboots
- Race conditions between bootout (async) and bootstrap

---

## The Fix

Enhanced `scripts/services.py:LaunchdManager.start()` with automatic retry logic:

### 1. **Better Cleanup**
- Longer timeout for `_wait_until_gone()` (3 seconds instead of immediate)
- Ensures launchctl finishes teardown before retry

### 2. **Multi-Level Retry**
```python
# Attempt 1: Normal bootstrap
launchctl bootstrap gui/501 /path/to/plist

# If exit 5:
# Attempt 2: Force bootout + cleanup + retry bootstrap
launchctl bootout gui/501/com.tradingplatform.service
# wait 3 seconds
launchctl bootstrap gui/501 /path/to/plist

# If STILL exit 5:
# Attempt 3: sudo retry (different user context)
sudo launchctl bootstrap gui/501 /path/to/plist
```

### 3. **Better Diagnostics**
- Clear logging of which attempt succeeded
- Passes through to `_explain_bootstrap_failure()` only if all attempts fail

### During Deployment

- No data loss (database unchanged)
- Cycles continue through deployment

### Post-Deployment
- Monitor service logs for 10 minutes: `./service.sh logs scheduler | tail -f`
- Verify cycles are running: look for "Cycle #X started" messages
- If services won't start, the error messages now include the exact commands to run

### If Service Startup Still Fails

The error diagnostics in `_explain_bootstrap_failure()` are unchanged and will tell you:
- If the label is DISABLED (how to re-enable it)
- If the interpreter path is wrong (how to reinstall)
- If it's truly a stale registration (exact cleanup commands)

Follow those instructions, or run:

```bash
python3 scripts/tp_enhanced.py fix-services
```
