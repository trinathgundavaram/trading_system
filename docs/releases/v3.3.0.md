## Why this release exists

Two related infrastructure bugs surfaced from real usage right after v3.2.0:
the UI kept showing "Failed to fetch" on multiple pages (self-resolving after
about a minute), and the Monitor tab's data-source panel showed several
providers as `NOT_CONFIGURED` even though data from them had clearly just
been fetched. Both traced back to gaps in how `scripts/services.py` and
`tp promote` manage a running service's identity and environment, not to
anything in the trading logic.

## What changed

### Service management (`scripts/services.py`)

- **Duplicate service registrations fighting for the same port.** A bare
  `python3 scripts/services.py install ui` (no `--suffix`) writes an
  UNSUFFIXED launchd label (`com.tradingplatform.ui`) alongside whatever
  version-suffixed one `tp promote` already installed
  (`com.tradingplatform.v3.2.0.ui`). Both get loaded, both have
  `KeepAlive`/`Restart=on-failure`/`ONLOGON`, and each one resurrects the
  instant the other is killed for port 8080 — an endless loop, confirmed on
  a real machine (`launchctl list` showed both labels loaded, both status
  `-15`, same duplication for `maverick`/`scheduler`). Every restart briefly
  drops the listening socket, which is what the browser saw as
  `Failed to fetch`. `install`/`start`/`restart` now call
  `other_registrations(name)` first and REFUSE with the exact removal
  commands if another registration of the same service exists, instead of
  silently colliding — `LaunchdManager`, `SystemdManager`, and
  `WindowsTaskManager` all implement it.
- **Provider credentials invisible to any `tp promote`-managed service.**
  `_service_env()` only ever injected 6 fixed variables into an installed
  service's environment — no market-data or Robinhood credential. A
  promoted service runs from a versioned worktree (`~/tp/versions/<tag>`)
  whose own `.env` never exists (`git worktree add` never checks out a
  gitignored path), so the only source of secrets those processes had was
  whatever `os.environ` launchd/systemd handed them — none. `_service_env()`
  now resolves every `SECRET_KEYS`/`OPTIONAL_KEYS` entry through
  `storage.secrets` and bakes the resolved values into the installed
  service's environment, matching what `tp run <tag>` already did for
  foreground runs.

### Provider key resolution (`mcp_clients/market_data.py`, `robinhood_mcp.py`,
`engine/live_trader.py`, `server.py`)

- Every provider's `self.key`/`self.secret` (Alpaca, Finnhub, Tiingo,
  TwelveData, AlphaVantage, FMP), Robinhood credential lookup
  (`robinhood_mcp.py:_credentials`, `live_trader.py:_login`), and the three
  server-side "is this configured" checks (`/api/sources`,
  `/api/robinhood/status`, `/api/real/summary`) used a bare `os.getenv()`,
  which only sees the current process's own environment. Switched all of
  them to `storage.secrets.get()`/`present()`, which additionally checks the
  OS Keychain — a single, machine-wide store, unlike a per-directory `.env`
  file — so a key mirrored in with `./scripts/tp secrets import .env`
  resolves identically from the primary checkout and every installed
  version. `/api/sources`'s `NOT_CONFIGURED` note text updated to mention
  the Keychain path.

## What this does NOT change

No scoring, sizing, or exit logic moved — `scripts/classify_change.py`
reports MINOR (`server.py` and `engine/live_trader.py` are behaviour paths,
not decision paths; nothing in `rules/` or `config.yaml` changed). No
database schema changed. No config keys changed.

## Behaviour you will notice

- `python3 scripts/services.py install|start|restart <name>` now refuses and
  prints exact removal commands if another registration of that service
  (different version suffix, including none) is already installed, instead
  of silently creating a second one.
- A freshly-installed service (`scripts/services.py install <name>`, or a
  `tp promote`) now has every configured API key/credential baked into its
  environment at install time. **Existing installed services do not pick
  this up automatically** — reinstall to get it:
  `python3 scripts/services.py install ui` (repeat for `scheduler`,
  `maverick`).
- The Monitor tab's data-source panel and the Robinhood status panel now
  correctly show a provider as configured whenever `storage.secrets` can
  resolve it (environment, `.env`, or Keychain) rather than only when it
  happens to be a literal environment variable in that specific process.

## Rollback

```bash
./scripts/tp promote v3.2.0
```

Rolling back reinstates: the duplicate-service-registration hazard (no
automatic protection against a bare `services.py install` colliding with a
promoted one), and provider credentials not reaching a promoted service's
environment (Keychain-mirrored keys still resolve for anything that already
went through `storage.secrets`, since that fix predates this release, but
the service-environment injection and the duplicate-registration refusal do
not exist on v3.2.0). No schema moved, so v3.2.0 can read a database this
version has written without any migration concerns.

## Known issues carried forward

Everything listed under v3.2.0 still applies. Additionally: the
duplicate-registration refusal and the service-environment secret injection
are both new in this release and have only been exercised against
synthetic/temp directories in a sandboxed environment, not against the real
machine that hit the original bug — recommended follow-up is to run the
cleanup commands from this release's fix on that machine and confirm
`service_ui.log` stops showing the restart loop.
