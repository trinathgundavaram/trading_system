## Why this release exists

v1.3.0 scoped the running-drawdown peak to the current paper-account epoch,
so a re-seed could no longer be mistaken for an all-time high. It left the
same bug in the intraday half.

Scoping only the peak meant a mid-day account reset still sat inside today's
intraday window, so the peak-to-trough scan ran straight across the
discontinuity. A re-seed downward — 1491 back to a 1000 `starting_cash` —
reads as a 33% intraday drawdown, which against the 2.0% cap blocks entries
for the rest of the day. For an accounting event.

The 2026-07-25 re-seed on the release machine stepped **up**, and an upward
step produces no drawdown. So the live data exercised the running half of this
bug and was completely silent about the intraday half. It surfaced only
because a test failed on an unrelated assertion and sent me looking.

## What changed

### §11 drawdown

- the epoch bounds the intraday window as well as the peak — `storage/database.py:update_drawdown` — §11
- `backfill_drawdown` drops pre-reset points on the epoch day only — `storage/database.py` — §11

Earlier days keep all their points. They belong to the previous account and
their intraday figures are self-contained and true for it; dropping them would
discard real history to fix a boundary problem that exists only at the
boundary.

### Tests

- `test_intraday_ignores_a_mid_day_reset` — covers the direction the live data
  could not
- `_equity()` writes today's points at `utcnow()` ascending rather than at a
  fixed 10:00 local

That fixture change is the other half of the failure. `init_paper_account`
stamps `created_at` with `utcnow()` and `update_drawdown` treats it as the
epoch boundary, so a fixed 10:00 wrote points that — depending on what time
the suite ran — landed *before* the account existed. They were then correctly
excluded, the peak query returned NULL, the fallback took the last value as
the peak, and the drawdown read 0.0% while the test asserted 1.6%. The code
was right; the fixture depended on the hour you happened to run it.

Points are now written forward from `utcnow()`, not backward, so they cannot
race the account creation immediately preceding them.

## What this does NOT change

Nothing about scoring, sizing or exits. No schema change. No config change.
`config_fingerprint` unchanged at `cc9a149613427f56`.

This is a patch: the control was already present in v1.3.0 and was computing
one of its two numbers incorrectly under one specific condition.

## Behaviour you will notice

Only on a day when the paper account is reset or re-seeded mid-session. Before
this, `paper_max_drawdown` for that day could read as the size of the reset
step and shut the session; now it reads the post-reset curve only.

If you have already run `backfill_drawdown.py` against a database with a
mid-day reset in it, re-run it — the recorded figure for that day was computed
across the discontinuity.
